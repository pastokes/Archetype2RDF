# EX: Properties Alignment — Standardization Review (Phase 2, Step 6)

Companion to `ontology_rdf_schema_comparison_v3.md` and `domain_range_compliance_v3.md`. Kept as a separate report by request, to avoid the other two growing too long to follow. Covers the review of the project's ~100 custom `EX:` catch-all properties: which can be aligned to existing standards (CIDOC-CRM's own properties, Dublin Core Terms, SKOS), which are genuinely custom domain facts needing only a formal `owl:DatatypeProperty` declaration, and which are application/interface plumbing that shouldn't be part of the formal ontology at all.

This work was prompted by a broader question about what it would take to produce a standalone OWL file (the next major deliverable after the current RDF/code error-fixing pass). Two things became clear in scoping that: (1) most of the script's existing class-hierarchy scaffold is already effectively a first draft of the OWL TBox, just interleaved with instance data rather than separated out; (2) the ~100 `EX:` properties are the biggest concrete gap — no `owl:DatatypeProperty`/`owl:ObjectProperty` declarations, no `rdfs:domain`/`rdfs:range`, and (per this review) roughly a fifth of them could be upgraded to standard vocabulary terms rather than formalized as custom properties, gaining real LOD interoperability rather than just RDF-DL correctness. See `domain_range_compliance_v3.md` §7 for the fuller OWL-file discussion this grew out of.

---

## 1. Summary of the triage

All ~100 distinct `EX:` properties currently used in the script, sorted into four buckets. This is not a per-property domain/range check the way the other two reports do for CRM properties — it's a classification pass, since the volume makes individual scrutiny of every property impractical and mostly unnecessary (most are simple literal-valued facts with no ambiguity).

| Bucket | What it means | Approx. count | Action |
|---|---|---|---|
| **1 — Standard vocabulary match** | A clean, honest fit exists in Dublin Core Terms, SKOS, or CIDOC-CRM's own `P3 has note` | ~18 properties, 9 target predicates | Swap the predicate, keep everything else the same. Real interoperability gain, near-zero cost. Being done now, one predicate at a time. |
| **2 — Interface/application plumbing** | UI rendering parameters, internal ordering, file paths, technical identifiers — not facts about manuscripts | ~20+ properties | Exclude from formal ontology entirely. No mapping, no diagram presence. Some are worth a separate question about whether they belong in the export at all (out of scope for this pass). |
| **2b — Explicitly internal** | Textually similar to Bucket 1 candidates but deliberately marked "internal only" (curatorial working notes) | 2 properties (`internal_note`, `internal_notes`) | Exclude from any public-facing mapping, for a different reason than Bucket 2 (privacy/scope, not technical irrelevance) |
| **3 — Genuine relationships / bigger modelling opportunities** | Not a simple vocabulary swap — either a real class-to-class relationship never modelled, or a recurring pattern worth documenting once | ~5–6 properties/patterns | Needs the project lead's judgement, not a mechanical fix. Logged individually below, not yet actioned. |
| **4 — Genuinely custom** | Domain-specific facts (physical measurements, boolean flags, counts) with no honest external match | ~50 properties | Keep as `EX:`, just add a formal `owl:DatatypeProperty` + `rdfs:domain`/`rdfs:range` declaration when the OWL file is built. No individual scrutiny needed — not part of this review's remaining work. |

Plus two small cleanup items outside the bucket system entirely (§4 below).

**General principle, applies across all buckets (added by project lead's decision, this pass):** any field or table named `legacy*` (e.g. `legacy_id`, `legacy_reference`) refers to the pre-Django state of the database and hasn't been used in ~15 years. These should not be included in the export at all — not mapped to a standard predicate, not kept as `EX:`, just dropped. For now, existing exported `legacy*` fields are parked in Bucket 2 pending a systematic check (see Future Work, §7) rather than removed immediately field-by-field as each is noticed.

**Note on DCTERMS naming, added for reference during this bucket's work (not a design question, just a clarification worth having on record):**

- Despite their noun-like names, every DC/DCTERMS/SKOS term used in this bucket — `dcterms:description`, `dcterms:rights`, `dcterms:date`, `skos:altLabel`, and the still-open `dcterms:identifier` — is an RDF property (a predicate/relation), never a class. In RDF there's no other kind of thing a property could be; `dcterms:description` used as `(subject, dcterms:description, value)` functions identically to a hypothetical `dcterms:hasDescription`. This is purely a Dublin Core naming convention (nouns, echoing how the original 15-element set described metadata in prose) rather than anything hidden in the semantics — unlike CIDOC-CRM's explicit verb-phrase style (`P3_has_note`), which makes the relational nature visible in the name itself.
- Separately, and more substantively: `dcterms:description` specifically has a **formally declared range of `rdfs:Resource`, not `rdfs:Literal`** — a deliberate DCMI design choice from 2008 (unlike `dcterms:date`/`dcterms:title`, which were given a literal range at the same time). Strictly, DCMI's own RDF schema suggests `dcterms:description` should point to a resource rather than a bare string — conceptually closer to the reification pattern discussed for evidence notes (§6) than to a plain literal. In practice this is not treated as a hard constraint: DCMI's own documentation explicitly frames domain/range declarations as "usage suggestions" rather than enforced rules, and plain-literal usage of `dcterms:description` (as done throughout this export, ~2,900 triples) is the dominant real-world convention across Linked Data generally. Not flagged as needing correction — logged for reference given this project's overall standards-conformance focus.

## 3. Corrections made during triage (worth recording, since they reversed an initial read)

- **`Image.caption` — moved from a Bucket 1 candidate to Bucket 2.** Initially considered for `dcterms:description`. Checked against the Django model directly: the field carries its own comment, *"no longer used, to be removed"* — explicitly deprecated by the DigiPal developers, not just low-value. Confirmed by the project lead: it's auto-generated from the image filename, used only to give a human-readable label in the admin interface. No mapping; stays exactly as it is, `EX.caption`, Bucket 2.
- **`Annotation.holes` — moved from an assumed Bucket 4 candidate ("holes in the parchment," a codicological fact) to Bucket 2.** Checked against the model: the field is annotation-rendering data (*"the holes to draw on the image thumbnail on the frontend"*), not a fact about the physical manuscript. Confirmed by the project lead: used to exclude a region from within an annotation shape — e.g. excluding a decorative border from the annotated text region. Interface/rendering plumbing, not domain data.
- **`MediaPermission.permission` — raised as a possible Bucket 1 candidate, reclassified to Bucket 2.** Values are an integer (`100`/`200`/`300`), not a rights statement, so `dcterms:rights` (already used for `Repository.copyright_notice`) was never the right target. Checked whether `dcterms:accessRights` fit instead, since the field is genuinely about who can access the resource: confirmed by the project lead as a real three-tier access scheme (image invisible to non-members; thumbnail-only for the public with full resolution for logged-in project members; fully open to everyone) — but it's DigiPal-specific, hard-coded in the Django application with no external standard or lookup table behind it, so the numeric code itself isn't independently meaningful outside this app. The five `MediaPermission` resources already carry the human-readable form on `rdfs:label` (e.g. "Open Access," "Have Licence," "No Licence," "Poor Quality"), which is the exportable fact; the raw integer is implementation detail. Same treatment as the adjacent `display_message` field (UI text for undisplayable images), already Bucket 2.
- **`Text.date_sort` — surfaced while implementing the `dcterms:date` swap, kept as `EX.date_sort`, reclassified to Bucket 2.** Initially assumed to be part of the same `date` field being swapped (both were mapped onto the same `text_uri` with the same `EX.date` predicate in the pre-swap code). Confirmed by the project lead: `date_sort` is not a date at all — it's an integer sort key used to order approximate/free-text date expressions correctly against each other (e.g. deciding whether "1010 CE" sorts before or after "early eleventh century"). Left as `EX.date_sort`, not swapped to `dcterms:date`. Leaning Bucket 2 (interface/application plumbing — a sort key, not a domain fact) rather than Bucket 4, though the project lead noted it isn't purely mechanical: the sort key is derived from a detailed underlying model of approximate dating that itself drew on a survey of scholarly users, so there's a genuine scholarly judgement embedded in how it's computed, even though the field's role in the export is just to enable correct ordering.
- **All `legacy*`-named fields — new general exclusion principle, moved to Bucket 2, now confirmed.** Raised while scoping the `dcterms:identifier` row: `Date.legacy_reference`, `HistoricalItem.legacy_reference`, `Scribe.legacy_reference` (and, more broadly, every `legacy_id` field across the model) refer to the pre-Django state of the database, unused for roughly 15 years per the project lead. Decision: no `legacy*`-named field or table should be part of the export at all, regardless of what it would otherwise map to. Checked what's actually in the current export: `HistoricalItem.legacy_reference` and `Reference.legacy_reference` were both live in the code (and hence the RDF); `Date.legacy_reference` and `Scribe.legacy_reference` were never read into the export despite appearing in this report's earlier `dcterms:identifier` coverage note; no `legacy_id` field is exported anywhere. **Confirmed by the project lead: all four (`HistoricalItem.legacy_reference`, `Reference.legacy_reference`, `Date.legacy_reference`, `Scribe.legacy_reference`) are genuinely legacy data and should not be included in the export.** The two live ones (`HistoricalItem.legacy_reference`, `Reference.legacy_reference`) are being removed from the code — see §2 status. The systematic check for any other `legacy*` fields quietly present elsewhere in the script remains logged under Future Work (§7).

Both corrections came from checking the Django model directly rather than guessing from the field name alone — the same discipline used throughout the other two reports.

## 5. Bucket 3 — Genuine relationships / bigger modelling opportunities (all resolved)

- **`Layout` dimension fields (`page_height`, `page_width`, `frame_height`, `frame_width`, `tramline_width`) — implemented.** Not originally logged as a Bucket 3 item, but surfaced and actioned in this session alongside `rdf:value`/`cataloguenumber` (§2), since both involve wrapping a literal in its own resource. Previously: one shared `Dimension_Historical_Item_<id>` resource per Layout, holding all five measurements as flat `EX:` literals with no unit captured. Restructured to CRM's documented dimension pattern — one `E54_Dimension` resource per measurement, each with `P2_has_type` (five new `E55_Type` resources distinguishing which kind of dimension), `P90_has_value`, and `P91_has_unit`; `P43_has_dimension` now fires once per dimension resource rather than once per Layout. Confirmed via a real-world implementation example (a weight measurement on a coin, from the UK Portable Antiquities Scheme, cited in a peer-reviewed paper on practical CIDOC-CRM implementation) that this is genuinely how established CRM-based projects model dimensions, not just a spec-only recommendation. **Unit hard-coded as millimetres, confirmed correct for DigiPal specifically by the project lead** — flagged clearly in the code and here, since other Archetype-based projects using this schema may use a different unit and would need to change this if so. A `MEASUREMENT_UNIT` (millimetre) resource already existed in the script, declared but never referenced anywhere — reused rather than duplicated; looks like a leftover from an earlier, unfinished attempt at this same fix.
- **`shelfmark`** (`Current_Item`) — **implemented.** A genuine identifier (a library shelfmark functions exactly like a catalogue number), now a real `P1_is_identified_by`/`E42 Identifier` link via a new `Shelfmark_Current_Item_<id>` resource, with the value on `rdf:value` — the same treatment `cataloguenumber` already has (§2), extending `rdf:value`'s use beyond that single original case as anticipated. URI is id-based (`Current_Item.id`) rather than value-based like `cataloguenumber`'s `CatalogueNumber_<cleaned_value>` pattern — a deliberate difference, not an inconsistency: `shelfmark` sits directly on the `Current_Item` row being iterated, which already has its own real database id, whereas `cataloguenumber` is a denormalized cached string read off `HistoricalItem` with no separately-iterated source row to draw an id from. The id-based approach also avoids a real collision risk `Current_Item.Meta.unique_together = ['repository', 'shelfmark']` implies: the same shelfmark string can legitimately recur under different repositories, which a value-based URI could not safely distinguish.
- **`locus`/`selected_locus`** (`Image`, `TextItemPart`, `Hand`) — **implemented**, with substantially more scope and design work than the original one-line note suggested. Turned out to cover four fields across three tables, not two as first logged; `TextItemPart.locus` had been missed entirely, and `Hand.selected_locus` was a fourth field not originally noted at all.
  - **Design history:** initially planned around CIDOC-CRM's `E46 Section Definition`/`P58 has section definition`, but checking the current stable spec (v7.1.1) directly showed both have been fully removed from the model, not merely discouraged — confirmed via the CRM SIG's own deprecation discussion, which explicitly extends the deprecation from `E46` to `P58`. Revised to the simpler, still-current pattern: a shared `E41 Appellation` resource (typed via `P2_has_type` → a new `Type_Locus` `E55_Type`, following the project's established typing convention) linked via `P1_is_identified_by`.
  - **Domain check:** confirmed via this script's *own* declared class hierarchy (not just CRM's abstract spec) that `Hand` and `TextItemPart`, both typed `TX7_Written_Text_Segment`, are transitively `E18_Physical_Thing` (`TX7_Written_Text_Segment → TX1_Written_Text → E25_Human-Made_Feature → E24_Physical_Human-Made_Thing → E18_Physical_Thing`, all already asserted in this script). `Image` (`E36_Visual_Item`) is not in that chain. `P1_is_identified_by`'s domain (`E1 CRM Entity`) is broad enough to apply uniformly regardless, but the project lead noted a genuine semantic distinction worth preserving: `Hand`/`TextItemPart`/`Item_Part` genuinely occupy the locus, whereas `Image` merely depicts it. Resolved by using `P1_is_identified_by` for the three physically-occupying entities and `P138_represents` for `Image` — the latter already an established pattern in this script (`Image → P138_represents → Item_Part`, for the whole item part), now extended to the more specific `Locus_Appellation`.
  - **Sharing/deduplication:** the `Locus_Appellation` URI is built deterministically from `(item_part_id, locus text)`, so when the same `Item_Part` and identical locus string recur across `Image`/`Hand`/`TextItemPart` (or repeatedly within one), they resolve to the same resource automatically — RDF being a set of triples, `rdflib` simply no-ops repeat `g.add()` calls, so this needed no extra code. Near-duplicate loci that differ only in string formatting (e.g. "72r" vs "fol. 72r") are **not** caught by this and will currently produce separate, unlinked resources — logged under Future Work (§7) rather than solved here, since fixing it needs either a normalization rule or a dedicated reconciliation pass, and is a materially harder problem than anything else resolved in this bucket. The project lead noted that genuine dual-numbering-system cases (e.g. a leaf with both a foliation and an unrelated pagination) can't be reconciled from string form alone regardless — but the shift from flat literals to real `Locus_Appellation` resources at least makes that kind of reconciliation *possible* in principle later (e.g. via `owl:sameAs` between two appellations known to denote the same place), where it structurally couldn't have been done with bare literals at all.
  - **`Hand.selected_locus` dropped, not migrated** — confirmed by the project lead as always identical to `Hand.locus` in the DigiPal data specifically, and judged to be internal bookkeeping rather than a distinct fact, even though the project lead believes it may carry real data in other Archetype-based projects using this schema. Moved to Bucket 2 rather than mapped.
- **`transcription`** (`Image`) — **resolved as removal, not a mapping.** Confirmed dead: 0 of 403 `Image` entities have any content in this field. Confirmed by the project lead: never used in DigiPal itself; to their knowledge used in only one other project, which was never made public and is now believed lost. Original suggestion of mapping this into the CRMtex apparatus already built out in this project (`TX6 Transliteration`) is dropped along with the field — see Future Work (§7) for the fuller, separate reason this needs proper modelling eventually, just not as this flat field.
- **`url`** (`HistoricalItem`, `Repository`, `Text`) — **resolved as removal, not a mapping.** Original Bucket 3 row was inaccurate on scope: `Reference` and `Source` don't actually have `url` fields on the Django model at all; `HistoricalItem.url` does and wasn't listed; `CatalogueNumber.url` exists on the model but isn't read anywhere in this script (same story as `CatalogueNumber` generally — only the denormalized `HistoricalItem.catalogue_number` string is used). Corrected scope: `HistoricalItem.url`, `Repository.url`, `Text.url`. Checked data: `Text.url` confirmed dead (1 of 385 entities has any triple at all, and that one is empty); `HistoricalItem.url` (13/1,553) and `Repository.url` (16/502) both sparsely but genuinely populated with clean, well-formed URLs. **All three dropped from the export regardless, on the project lead's judgement:** `HistoricalItem.url` values are long outdated/broken and were never the semantically right thing to capture anyway — what they gesture at ("where to find digital images of this item") is exactly the kind of link this project's broader LOD/IIIF goals (via Biblissima, see §7) are meant to provide properly, not a URL field inherited from the old schema. `Repository.url` (the institution's own website, e.g. the BnF's) is semantically sounder and more durable, but too sparse to be worth keeping, and the project lead is fairly confident it isn't used by other Archetype-based projects either. **The underlying concept is kept in mind for the eventual OWL file** (a proper `url`/external-link property, for whenever there's good IIIF-based data worth attaching), just with no current instance data mapped to it.
- **The `dubitable` pattern** — **implemented**, with corrected scope. Original row (`Archive`, `ItemOrigin`, `HistoricalItemDate`, `HandDate`/`HandPlace`) was inaccurate: confirmed via a careful field-by-field re-read of the Django model that `Hand` has no `dubitable` field at all, and `HandDate`/`HandPlace` aren't real database tables in the first place — they're synthetic `E13_Attribute_Assignment` node names this export script itself invents to represent `Hand.assigned_date`/`Hand.assigned_place`, so there was never a real column for a `dubitable` value to come from there. The project lead's own recollection matched the (mistaken) original report here too, but confirmed via direct SQL inspection that no such field exists. **A fourth field surfaced that the original row missed: `Owner.dubitable`**, structurally different from the other three — it sits directly on the `Owner` resource (`E39_Actor`), not wrapped in its own `E13_Attribute_Assignment` node. Real scope: `Archive.dubitable`, `ItemOrigin.dubitable`, `HistoricalItemDate.dubitable`, `Owner.dubitable` — 1,658 triples total, genuinely populated (1,354 `false`/304 `true`), not a dead field.
  - **Also checked, at the project lead's prompting: `digipal.date_evidence` and `digipal.place_evidence`, in case either carried a `dubitable`-equivalent.** Neither does. `date_evidence` is a real, substantially populated table (1,580 rows of genuine scholarly content) that this export currently doesn't read from at all; `place_evidence` is completely empty and has no corresponding Django model — consistent with it being unused/orphaned. Both out of scope for the immediate `dubitable` question, but see Future Work (§7) for `date_evidence` specifically, since real data shouldn't stay silently excluded.
  - **CRMinf checked, as originally flagged.** It does have relevant machinery (`I2 Belief`, `I7 Belief Adoption`, `J2 concluded that`, etc.) but it's built for reifying a doubted fact into a full `Proposition Set` held as a `Belief` by a specific `Actor` — a genuine argumentation structure, not a lightweight flag. More decisively: a CIDOC-CRM SIG issue thread on exactly this question ("Belief Values") shows the CRM community's own guidance on expressing simple statement-level uncertainty is still unresolved as of the most recent discussion found, weighing `E13 Attribute Assignment`, a lighter `R1 Reliability Assessment`, and full `CRMinf` against each other without landing on a recommendation — with some in the community sceptical that quantified belief is worth the complexity for a case like this at all. So unlike the `has_evidence_note` decision (§6), there's no settled CRM-native target to align with here. **Resolved with a new `E55_Type` resource (`Type_Dubitable`), applied via `P2_has_type` only when the flag is true** — mirroring the project's existing `ACCEPTED_TYPE` pattern (`HandDate`/`HandPlace`), and preferred over a plain boolean property after discussion: `P2_has_type` reads correctly as "this assertion is of type Dubitable," in the same idiom CRM already uses elsewhere in this script for classifying assertions, rather than introducing a bespoke property with no settled CRM precedent to anchor it to. The trade-off accepted: "not dubitable" and "never assessed" both mean the same thing (absence of the type link) rather than being distinguished, which the project lead judged an acceptable simplification given the underlying `false`/`NULL` distinction in the source data isn't itself fully reliable.
  - **`Owner.dubitable`'s placement was initially characterized as structurally anomalous compared to the other three** — sitting on `owl:sameAs`-linked `E39_Actor` rather than its own `E13_Attribute_Assignment`. Checking the prior `Owner`/`Repository` discussion in `domain_range_compliance_v3.md` confirmed this was a genuine, separate modelling error, not just an awkward fit: `Owner` is a linking/assertion record between an item and its owner, not the owner itself, so `owl:sameAs` was asserting numerical identity where none exists. **This was fixed in full as part of closing out `dubitable` cleanly**, since `Type_Dubitable` needed an actual assertion-shaped resource to attach to for all four fields to be uniform: `Owner` retyped `E13_Attribute_Assignment`, its `owl:sameAs` links to `Person`/`Institution`/`Repository` replaced with `P141_assigned`, and the separate `itempart_owners` linking loop's `P50_has_current_keeper` (previously misapplied to `Owner`, and factually wrong regardless of `Owner`'s typing — confirmed via SQL that the underlying table holds full historical ownership chains, sometimes several owners per item, not a single current custodian) replaced with `Owner --P140_assigned_attribute_to--> Item_Part`. `P50_has_current_keeper` is now used exclusively for `CurrentItem → Repository`, consistent with `CurrentItem` being the class actually meant to carry current-state facts. All four `dubitable` fields (`Archive`, `ItemOrigin`, `HistoricalItemDate`, `Owner`) are now uniformly `E13_Attribute_Assignment`-typed, with no remaining exception case.
  - **One unrelated, pre-existing bug found and fixed along the way**: while checking the `Owner`/`itempart_owners` fix, a naming collision at the separate `ItemPartItem` (`data['itempartitem']`) loop was found — a locally-scoped `F5_Item_uri` was accidentally built with the *same* URI as `Item_Part` itself, producing a meaningless self-`sameAs` triple. Worse, once traced through, the surrounding code also asserted both `Historical_Item` and `Item_Part` as `owl:sameAs` the same `F3_Manifestation` resource, which — by `sameAs`'s transitivity — falsely implied `Historical_Item` and `Item_Part` are identical, directly contradicting the correct `P46_is_composed_of` relationship stated on the line immediately above it. Confirmed the whole block was redundant regardless: the script already declares `Historical_Item`, `Item_Part`, and `Current_Item` as `rdfs:subClassOf` both `FRBRoo.F5_Item` and `FRBRoo.F3_Manifestation` at the class level (lines 156–161), so no per-instance `sameAs` was needed to establish either typing. The entire block was removed.
  - **Separately, `Archive`'s polymorphic target was checked while confirming the above** — the code only handles `content_type_id == 43` (`Place`) when resolving what `Archive` points to, silently dropping anything else via a debug `print()`. Confirmed by the project lead: harmless for DigiPal specifically, since `43` is in practice the only content type ever used as a target here, even though the underlying table is designed to be polymorphic (able to point at other entity types too). Flagged as something that would need proper `case`-style handling on a per-project basis for other Archetype-based projects that do use other target types for this link — not a DigiPal data-completeness bug, just a portability limitation worth documenting.
- **The `Reference` table's own standing — is it still meaningful, or a dead legacy holdover?** Surfaced while scoping the `dcterms:bibliographicCitation` swap for `Reference.full_reference` (always empty, see §2 above). `models.py` itself comments `Reference` as "References in legacy db." In the current export it's linked from only one place, `Scribe.reference` (a `ManyToManyField`), and only sparsely — 91 of 576 Scribes (~16%). The other place it's used in the Django model, `DateEvidence.reference`, isn't read by `creation_rdf.py` at all currently, so that link doesn't reach the export either way. None of the 440 `Reference` resources carry a real label (`name_index` is a single-character sort key, not a label). This looks different in kind from `Source` (used pervasively as the `source` field on `Description`, `HandDescription`, `CatalogueNumber`, `ItemPartAuthenticity`, etc., with its own display apparatus — `priority`, `label_slug`, `label_styled`). Whether the sparse `Reference` data is meaningful and worth keeping, or itself a legacy artefact, needs the project lead's judgement — logged here rather than resolved, since it goes beyond a predicate mapping and touches modelling questions from the earlier steps of this project.
- **Generic comments vs. evidentiary notes — two pre-existing, inconsistent patterns found for the same kind of content, reconciled under `P3_has_note`.** Surfaced while implementing the `P3_has_note` row above. `Layout.comments` was already mapped to `rdfs:comment` (an RDFS schema-documentation predicate, not really intended for instance-level domain content) while `HistoricalItemDate.evidence` was already mapped to `crm:P3_has_note` (CIDOC-CRM's own container for informal descriptive content) — an inconsistency the project lead judged, on inspection, to be an artefact of `Layout.comments` having been done at an earlier stage, before the `P3_has_note` pattern was settled on, rather than a deliberate distinction. Also surfaced in scoping: `Date.evidence`, a field distinct from `HistoricalItemDate.evidence` despite the similar name, not previously listed under this row at all. Separately, the project lead wanted evidentiary notes (`Owner.evidence`, `Date.evidence`, `HistoricalItemDate.evidence`) to remain distinguishable from genuinely generic comments (`Layout.comments`, `Description.comments`, `Hand.comments`) rather than collapsing both under a single indistinguishable predicate. Resolved with a new `arch:has_evidence_note`, declared `rdfs:subPropertyOf crm:P3_has_note` — see §6 for the fuller discussion of this choice, logged as one to revisit with CIDOC-CRM domain experts rather than treated as certainly correct.
- **`ItemPart.notes` — a third instance of the same `rdfs:comment` pattern, found in a follow-up check after the rest of the `P3_has_note` row was already implemented.** Confirmed empty for DigiPal specifically via SQL, but the project lead chose to include it in the swap regardless, since the same table underpins other Archetype-based projects (Models of Authority, Exon Domesday, etc.) where it can't be ruled out as populated. Judged clearly generic rather than evidentiary in nature, so mapped to plain `crm:P3_has_note` rather than `arch:has_evidence_note`.

## 6. Decisions flagged for future review with CIDOC-CRM domain experts

Kept as a running list, at the project lead's request, of choices made pragmatically in this project rather than with full confidence they're the "correct" CRM-idiomatic answer — worth raising if the opportunity arises to check them against expert judgement.

- **`arch:has_evidence_note` as `rdfs:subPropertyOf crm:P3_has_note`, rather than reifying notes with `P2_has_type`.** To keep evidentiary notes (`Owner.evidence`, `Date.evidence`, `HistoricalItemDate.evidence`) distinguishable from generic comments (`Layout.comments`, `Description.comments`, `Hand.comments`) without collapsing both under a bare `P3_has_note`, two options were considered: (a) a custom sub-property declared via `rdfs:subPropertyOf`, which was chosen — one declaration, no change to the data's structure, still correctly reads as `P3_has_note` under RDFS entailment; or (b) the fuller CRM-native route of reifying each note as its own `E33_Linguistic_Object` resource (text on `P190_has_symbolic_content`, category on `P2_has_type`), which is arguably the more idiomatic CRM pattern for typed descriptive content but would add a new resource per note instance (roughly 3,100 across the affected fields) for a distinction that's currently just a fixed binary category with no further per-note metadata anticipated. Chosen (a) for its much lower structural cost, given the project lead's preference to avoid added complexity where the actual need is just the category distinction — but logged here since (b) is plausibly what a CRM purist would consider the "correct" approach, and the trade-off was made on pragmatic grounds rather than a settled view of best practice.
- **The `dubitable` pattern and CRMinf** — see §5. Checked: CRMinf has relevant machinery (`I2 Belief`/`I7 Belief Adoption`/`J2 concluded that`) but requires full reification into a `Proposition Set`+`Belief`+`Actor` structure, and — more decisively — the CRM SIG's own community discussion on expressing simple statement-level uncertainty is itself still open and unresolved as of the most recent thread found, with no settled recommendation between `E13 Attribute Assignment`, `R1 Reliability Assessment`, or full `CRMinf`. Resolved pragmatically with a new `Type_Dubitable` (`E55_Type`) applied via `P2_has_type`, matching the existing `ACCEPTED_TYPE` pattern already in the script, rather than attempting to build on unsettled CRM guidance — logged here as a decision made without a clear expert consensus to defer to, should the opportunity for real expert input arise. The "not dubitable" vs. "never assessed" distinction is not preserved (both read as an absent type link) — an accepted simplification, not flagged as needing revisiting unless the underlying data's `false`/`NULL` distinction turns out to matter more than currently believed.

## 8. General RDF consistency sweep (this session, after Buckets 1–3 closed)

At the project lead's request, a systematic sweep of the regenerated RDF was carried out looking for inconsistencies or errors beyond the specific properties/buckets already tracked — cross-checking against the code and prior reports where relevant. Findings:

**Fixed as part of this sweep:**
- **`Hand` → `Item_` backwards `P46_is_composed_of`, plus a `sameAs`-transitivity consequence.** A leftover/duplicate line (likely an earlier draft of the correct `Hand --P46_is_composed_of--> Graph` pattern found later in the same loop) asserted `Hand --P46_is_composed_of--> Item_<id>` — backwards on its own terms, and made worse because that `Item_<id>` URI is `sameAs`-linked to `Current_Item` elsewhere, transitively implying "Hand is composed of Current Item." Removed entirely; the correct fact was already separately and correctly stated via `Item_Part --P56_bears_feature--> Hand`.
- **`HistoricalItem.catalogue_number` empty-string bug** — 23 items were falsely sharing one meaningless, empty `CatalogueNumber_` resource via `P1_is_identified_by`, the same "empty string passes `pd.notna()`" pattern found repeatedly elsewhere this session (`keywords_string`, `locus`, `full_reference`). Fixed with the same `str(x).strip() != ''` guard.
- **`Decoration.catalogue_references` empty-string bug** — same pattern, 6 of 84 values were empty strings exported as empty triples. Fixed alongside the future-work note above (§7).
- **`Hand.internal_note`, `Image.internal_notes`, `Annotation.internal_note` — removed from the export entirely.** These had been mapped to `EX:` (unmapped catch-all) rather than any standard vocabulary during the Bucket 1 triage, on the grounds that they're explicitly marked "internal only" curatorial content (§1, Bucket 2b) — but the code was still unconditionally exporting them regardless, which the sweep caught as a live contradiction between the report's stated intent and actual behaviour. Content sampled during the check reads as genuine scholarly working notes (dating/attribution reasoning, "CHECK"/"FIX" reminders) rather than personal or confidential data, but not material meant to represent settled, citable claims in a published LOD dataset. Commented out, not deleted, matching the project's established convention for deliberate omissions.

**Checked and confirmed benign, no action taken:**
- Two literal `"None"`-string values found (`Decoration.colours`, `LatinStyle.style`, one occurrence each) — both fields already have correct `pd.notna()` guards in the code, so this is a genuine source-data quirk (the text "None" was apparently entered as a value) rather than an export bug.
- 62 `TextItemPart` resources carrying almost no properties beyond their type — confirmed still correctly linked into the graph via `TXP4_has_segment` from their parent `Text`, just reflecting genuinely thin source data (consistent with `locus` being the only consistently-populated field on this table, per the earlier `locus` investigation). Not orphaned, not a bug.
- No recurrence of the systemic float-ID bug (`.0` in URIs) found anywhere in the current export.
- No other instances of the `sameAs`-collision anti-pattern (two distinct entities asserted `sameAs` the same shared resource) found beyond the one already fixed.
- No other malformed URIs found (checked for double-underscore and empty-segment patterns; the double-underscores that do appear are expected, from punctuation like "." being cleaned into "_").
