## 3. Namespace redesign

Triggered by the ARCH/EX split being cleaned up before the OWL file is built (nothing published yet, so no cost to getting this right now rather than living with it).

**Two separate namespaces, kept apart deliberately:**

- **Vocabulary namespace** (classes and properties — what the OWL file declares): `https://w3id.org/archetype/ontology/`, prefix `archetype:`.
- **Data namespace** (this dataset's individual resources): `https://digipal.eu/data/`, prefix `data:`.

**Why kept separate**: the Archetype model is reused across other projects (Models of Authority, Exon Domesday, etc.), not just this DigiPal/pstokes export. Mixing vocabulary and data into one namespace would make the vocabulary look like it belongs to one dataset rather than being a shared, stable thing multiple datasets point at. This applies equally to *properties*, not just classes — properties are schema/TBox elements exactly like classes (Peter's own observation, and correct): other Archetype-based projects would want to reuse `archetype:has_evidence_note` or `archetype:dubitable`-type properties, but never `data:Idiograph_9657`.

**Why `w3id.org` rather than a digipal.eu or archetype.ink path:**
- `archetype.ink` (the project's original domain for the general model) is no longer controlled by the project, and is confirmed **actively squatted** by an unrelated third party — ruled out.
- `digipal.eu` is stable and controlled long-term, but is specifically the DigiPal *dataset's* domain, not a good fit for a vocabulary meant to be shared by other Archetype-based projects.
- `w3id.org` ("permanent identifiers for the web") is the standard semantic-web mechanism for exactly this situation: a domain-independent, community-maintained redirect, registered via a one-time GitHub pull request, so the ontology's identity survives even if hosting moves. Several CIDOC-CRM-adjacent ontologies use it for the same reason.
- **Not yet registered.** `https://w3id.org/archetype/ontology/` does not currently resolve to anything. This needs a PR to the w3id.org repo before the IRI is dereferenceable — flagged clearly in `creation_rdf.py` as a `# TODO`, and here, so it isn't forgotten before anything is published or shared outside the project. Can draft that registration config whenever wanted.

**Versioning**: term URIs themselves stay **unversioned** (`archetype:GraphComponent`, no version segment), matching CIDOC-CRM's own convention (terms at the plain `.../cidoc-crm/`, only the distributed file snapshot dated, e.g. `.../7.1.3/`). The version for this draft is **0.1**, to be expressed as `owl:versionIRI <https://w3id.org/archetype/ontology/0.1/>` on the ontology declaration once the OWL file exists — not baked into individual term identities, so a future revision doesn't force every consumer to update every reference.

**Prefix naming**: the data namespace's *prefix label* (as opposed to its URI) was renamed from the inherited `ex:` (a generic RDF-tutorial placeholder name, used historically as a catch-all for anything not mapped to a standard vocabulary) to `data:` — considered `digipal:` too, but since the URI itself already says `digipal.eu`, `data:` was judged clearer without being redundant.

## 4. Namespace migration carried out in `creation_rdf.py`

(Implemented by Peter, checked by Claude at each step — see below for what was checked.)

- `ARCH` repointed from `https://digipal.eu/` to `https://w3id.org/archetype/ontology/`. Since every class reference in the file already went through `ARCH[...]`/`ARCH.X` consistently (checked directly — no hardcoded literals for classes anywhere), this one-line change alone correctly repointed all class references.
- `EX` renamed to `DATA` and repointed from `http://digipal.eu/ontology#` to `https://digipal.eu/data/`.
- **Found and fixed along the way**: instance URIs were *not* consistently using the `EX` namespace object — 176 of them were hardcoded as raw literal strings (`URIRef(f"http://digipal.eu/ontology#...")`) rather than going through `EX[...]`. All converted to proper `DATA[...]` bindings so they can't drift out of sync again.
- **Found and fixed along the way (the more significant catch, Peter's own observation)**: of the ~100 custom `ex:`-prefixed terms, 97 triples' worth were actually *properties* (predicate-position uses like `EX.vernacular`, `EX['dubitable']`), not individuals — these had been swept into the data-namespace rename along with genuine instance URIs. Corrected: all 89 distinct custom properties moved to the `ARCH`/vocabulary namespace instead (matching how `arch:has_evidence_note`, the one property already formalised, had always correctly lived there). Identified by triple position (a property is always the middle argument of `g.add((subject, predicate, object))`, flanked by commas), not by name — "property vs. individual" isn't decidable from the token alone.
- `http://` → `https://` fixed on the `DATA` namespace (an initial slip, caught and corrected) so both namespaces are scheme-consistent.
- Verified after each change by parsing the regenerated export directly with `rdflib` (not just diffing text): triple count held at exactly 1,079,654 throughout (confirming no data content was lost or altered, only URIs), the class/property/individual split confirmed correct via direct queries (e.g. `archetype:vernacular`: 1,363 triples; `data:vernacular`: 0), and no leftover old-namespace strings anywhere in the file.

## 4a. `HistoricalItemDate` dropped from the export (2026-09-21)

Surfaced while classifying `archetype:vernacular` for the datatype-property pass: the property appeared on two different resource types — `Historical_Item` directly (1,347 triples), and the `HistItemDate_<id>` `E13_Attribute_Assignment` nodes produced by the `HistoricalItemDate` table (16 triples). Investigation:

- The project lead clarified the intended semantics: `HistoricalItemDate` records a *writing event* (production or later addition — `addition` false/true respectively) carried out on an item at a given date, not a property of the item itself. Its `vernacular` flag means "does the text added at this writing event contain any vernacular?" — `Historical_Item.vernacular` is nominally an aggregate over these (true iff at least one associated writing event is true), though not guaranteed consistent in the data.
- Checked directly against the RDF export (`rdflib`): only **17** `HistItemDate_<id>` resources exist, matching the 17 rows in the source SQL table exactly (confirming the export itself isn't dropping rows). Against 1,553 Historical Items total, that's ~1% coverage.
- The project lead checked the same table in the Models of Authority database and confirmed it is empty there too, and expects the same for Exon Domesday (not yet checked directly). **Conclusion: an experiment that was never carried through, not a feature in active use.**
- **Decision: drop the entire `HistoricalItemDate` export block** (the loop building `E13_Attribute_Assignment`/`P140_assigned_attribute_to`/`P141_assigned`/`has_evidence_note`/`vernacular`/`addition`/`dubitable`-typing for this table), commented out rather than deleted, matching the project's existing convention for deliberate omissions (cf. `internal_note`/`internal_notes` fields).
- **Consequence for the OWL file**: resolves the two-domain question cleanly — `archetype:vernacular` is a single property, domain `archetype:Historical_Item`, range `xsd:boolean`. No split property needed.
- **Consequence for other tracked figures**: this table was one of `arch:has_evidence_note`'s three usage sites (`ex_properties_alignment_v1.1.md` §2, `P3_has_note` row) and one of the four `dubitable` fields (§5) — corrected in that report (now v1.1) rather than here, since it's a properties-report concern, not an OWL-scope one. `dubitable`'s `true`-count drops from 304 to 301 (confirmed via the RDF export: exactly 3 of the 304 `Type_Dubitable`-typed resources were `HistItemDate_*`).
- Not yet actioned in code at time of writing this entry — Peter Stokes to make the change and regenerate the export (v7), to be verified as usual.

## 4c. FRBRoo replaced with LRMoo, floating-class import resolved (2026-09-22)

Raised while checking the HermiT/Protégé output on `archetype_ontology_0.1.ttl`: `frbroo:F3_Manifestation`/`frbroo:F5_Item` (used for `Historical_Item`, `Item_Part`, `Current_Item`) were "floating" outside the class hierarchy in Protégé, since FRBRoo was referenced but never `owl:imported` (§ header TODO, now removed).

- **Checked the real FRBRoo vocabulary directly** (its IFLA namespace, `http://iflastandards.info/ns/fr/frbr/frbroo/`, via its published N3 file) rather than assuming an import would fix it. Found the import alone wouldn't have been enough: `frbroo:F3_Manifestation` isn't actually a valid URI in FRBRoo at all — the real class is the short-form `frbroo:F3` ("Manifestation Product Type"), aliased to `frbroo:F3_Manifestation_Product_Type`, not `F3_Manifestation`. (`frbroo:F5_Item` was a genuine alias and would have been fine.)
- **Checked Erlangen's `efrbroo` OWL implementation** as the obvious machine-readable alternative — ruled out: different namespace (`erlangen-crm.org/efrbroo/`, wouldn't connect to the `frbroo:`/IFLA URIs already used), and it bundles its own older CIDOC-CRM 5.0.4 under yet another separate namespace, unreconciled with the CIDOC-CRM 7.1.3 already imported here.
- **Decision: switch to LRMoo** (formerly "FRBRoo" — FRBRoo is being deprecated by IFLA, LRMoo is the current, IFLA-approved successor, v1.1.1). Checked directly against the LRMoo v1.1.1 spec and its published OWL file (`https://cidoc-crm.org/extensions/lrmoo/owl/1.1.1/LRMoo_v1.1.1.owl`, the same publishing pattern already used for CRMtex): it declares `lrmoo:F3_Manifestation` and `lrmoo:F5_Item` under exactly those local names — no renaming needed beyond the prefix/namespace — and imports CIDOC-CRM 7.1.3, matching what's already imported here (no version conflict, unlike Erlangen).
- **Implemented**: `frbroo:` (namespace `iflastandards.info/ns/fr/frbr/frbroo/`) replaced with `lrmoo:` (namespace `iflastandards.info/ns/lrm/lrmoo/`) throughout; `owl:imports` now includes the LRMoo OWL file; header TODO rewritten to record this decision; `dcterms:description` updated. Verified: `rdflib` parses cleanly, 341 triples (was 340, +1 for the new `owl:imports` triple), class/property counts unchanged (18/1/57) — confirms this was a pure namespace/import swap, no content change.
- **Not just a rename — flagged for future attention**: the two classes' CIDOC-CRM superclasses differ between FRBRoo and LRMoo. `F3_Manifestation` moves from `⊑ E55_Type` to `⊑ E73_Information_Object`; `F5_Item` moves from `⊑ E84_Information_Carrier` to `⊑ E24_Physical_Human-Made_Thing` (more concretely physical). Noted inline on `Item_Part`'s `rdfs:comment` since it may bear on the already-open "is `F5_Item` the right fit for `Item_Part`?" question (`domain_range_compliance_v3.md` §7) — not resolved by this change, just newly-relevant context for whenever that's revisited.

## 4g. `ontologie` block stops self-declaring; hand-copied class-hierarchy scaffold removed from `creation_rdf.py` (2026-09-22)

This removes the drift risk without hand-copying, and gives anyone loading the deposit everything needed to reason over it locally, independent of what data.biblissima.fr's platform does by default. **Not yet resolved**: whether to also materialise inferred `rdf:type` triples into the published data itself, for consumers who query without a reasoner — deferred, flagged as a possible future step rather than decided now.
- **Implemented in `creation_rdf.py`**: the entire hand-copied `subClassOf`/`subPropertyOf` scaffold (schema-level only — no instance/ABox data touched) removed, now that it is fully redundant with the formal ontology plus its vendored imports.

## 4i. `HandDescription`/`P3_has_note` property misuse fixed — a real bug surfaced by vendoring the imports (2026-09-22)

P3_has_note HandInstance_1269 HandDescription_1701 ...)` — an `IRI cannot be cast to OWLLiteral` failure). CIDOC-CRM's real OWL file declares `P3_has_note` as literal-valued; every other use of it in `creation_rdf.py` (4 sites) correctly passes a `Literal`, but the `handdescription` table loop (already flagged with two of Peter's own unresolved `TODO`s) used it to link `HandInstance` to a separate `HandDescription` resource — 427 triples, confirmed via `rdflib` to be the only IRI-valued `P3_has_note` triples in the export (2,122 of 2,549 total were correctly literal-valued).

- **Root fix, iterated over three rounds**: (1) first proposed retyping `HandDescription` from `crm:E62_String` to `crm:E33_Linguistic_Object` and linking via `crm:P67_refers_to`; (2) Peter objected that E33's scope note is about literary/historical texts, not documentation — a good catch; re-examined the block and found the script *already* uses `source_uri crm:P70i_is_documented_in hand_desc_uri` one line below, whose formal CIDOC-CRM domain (`P70_documents`, domain `E31_Document`) requires `hand_desc_uri` to be an `E31_Document` anyway — settled on **`crm:E31_Document`** instead, both a better semantic fit and required by a property already in use on the same resource, and consistent with the project's existing precedent (`Date`'s evidence-document node is also `E31_Document`); (3) Peter's first implementation attempt swapped the predicate (`P3_has_note`→`P67_refers_to`) but left the subject/object direction and the type unchanged — caught before regenerating further, since keeping `HandInstance` as `P67_refers_to`'s subject would leave a new, still-wrong domain assertion (`P67_refers_to`'s domain is `E89_Propositional_Object`, which `HandInstance` is not); flagged and corrected to `hand_desc_uri crm:P67_refers_to handinstance_uri` (description refers to the hand instance) with `hand_desc_uri` retyped `E31_Document`.
- **Verified by Claude, full protocol** against the v15 baseline: `py_compile` clean; script diff exactly two lines (the type line, the flipped/renamed property line); triple-diff **854 removed / 854 added**, all four buckets exactly 427 each (`E62_String` type removed, `P3_has_note` triples removed, `E31_Document` type added, `P67_refers_to` triples added); confirmed directly that all 427 new `P67_refers_to` triples have `HandDescription_*` as subject (0 wrong-direction). Nothing else in the ~1,014,667-triple export touched. `v16` set as the new baseline.
- **Left alone, per scope**: the two other `TODO`s on this block (`Unify Descriptions across the database?`, and whether `source_id`'s `P70i_is_documented_in` direction is itself backwards) — flagged as open, not part of this fix, Peter's call whenever revisited.
- **Broader takeaway**: this validates the vendoring decision in §4g — a real, several-hundred-triple modelling bug that neither `rdflib` parsing nor any previous check caught was only surfaced once Protégé had CIDOC-CRM's actual property declarations loaded locally.
